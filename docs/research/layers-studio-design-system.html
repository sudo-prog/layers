LAYERS Studio — the design system

This artifact is the visual language the next LAYERS surface should be built in. It is derived from the graphite glass system in docs/design-graphite.md — the glass, the contrast discipline and the panel-over-canvas structure are unchanged — with one layer added: a chosen radius ladder, one warm accent instead of a cool blue, and menus that emerge from underneath the canvas plane rather than dropping off a trigger.

The reference that prompted it was a studio-management surface: dense thread lists, a small colour-coded status dot per row, and menus that slide out from under the top plane. Those are posture choices, not copied chrome — the layout, the panels and the tokens are LAYERS's own.

1 · Surfaces

Warm charcoal, not neutral grey and not tinted near-black. The lift between steps is deliberately narrow: a panel should read as one material, not as a stack of different ones.

The accent is warm amber on purpose

Two of the most common generated-dark-UI tells are a near-black ground with an acid-green or vermilion accent, and an indigo accent chosen by default rather than by reason. Amber is neither: it is warm against a cool charcoal, it clears 3:1 as a boundary, and it reads as a studio signal rather than a system colour. It is used for exactly one thing — the active trigger, the selected row and focus.

text-tertiary is lighter than it looks like it should be

The graphite system uses #8b95a3 for tertiary text. At this system's surface ramp that measured 3.96:1 — below the 4.5:1 floor — so it is #a1a8b2 here. The graphite doc hit the identical trap with #6b7280, which failed AA at any alpha because the colour itself was too dark for small text on a dark ground. A muted grey that looks fine on a swatch routinely fails in situ.

2 · The radius ladder

Six steps, and they are related rather than arbitrary. The rule that makes them hold together: outer radius = inner radius + padding. A 20px panel holds a 10px control because it has 10px of padding. A 12px chip holds an 8px inset because it has 4px.

20window / panel
16menu
14card / frame
12chip
10control / button
999pill / dot

Two worked examples from the artifact above. Neither is decorative — the arithmetic is what stops nested corners looking pinched.

3 · The sliding menus

This is the behaviour the brief asked for, and it is a structural decision, not an animation trick. The menu is a sibling of the toolbar, not a child of the trigger button. Three planes, in paint order:

2toolbarsits on top; its bottom edge is the ceiling the menus hang from
1menustarts tucked 12px UP under the toolbar, slides down over the canvas
0canvasbleeds under the panels; the backdrop filter blurs it

Because the hidden state is translated up rather than merely faded, the open animation is a genuine slide out from underneath the plane. A dropdown that grows downward from the pill it belongs to reads as attached to that pill; one that drops from the plane reads as attached to the surface.

The z-index trap this fell into

The first version put the menu band inside .canvas, which was natural — the menus belong to the canvas visually. But .canvas carries z-index: 0 so the panels can sit above it, and a positioned element with a z-index establishes a stacking context. Everything inside it is then ranked against the other children of .canvas, and can never rise above a sibling of .canvas — including the left panel. The menu painted behind the panel and its left edge was clipped.

Geometry assertions passed this. They measured the menu's box, and the box was correct; what was wrong was what covered it. Vision review caught it. The fix was structural: the menus moved out of .canvas to be a child of .window and a sibling of the panels, at the same z-index (1) as the panels, with the toolbar still at 2.

The trigger's aria-expanded and the menu's own id are wired properly, and the trigger is a real <button> — the seam between trigger and menu is only visual.

4 · Interaction states

Motion is 150–220ms with cubic-bezier(0.2, 0, 0, 1) — the standard ease-out. Nothing animates on hover except colour; the press state is a scale(0.96), never smaller, because anything below 0.95 feels exaggerated.

prefers-reduced-motion removes every transition, including the menu slide. The menu still opens — it just stops moving.

Uppercase is used for exactly two things: panel titles and section labels, both at 11px with 0.08em tracking. It is not a default treatment for every label — that is a generated-UI tell.

6 · Contrast

Measured on the darkest surface the glass can composite to, which is the binding case — a panel over a bright canvas. Every text token clears WCAG AA.

Computed in the page from the live token values, so it reflects this palette rather than a remembered one. Which canvas is binding depends on the theme: in dark mode it is the white one, in light mode the black one, because that is the case pulling the composite furthest from the text colour. The labels name it rather than asserting one canvas for both themes.

7 · Rules that were load-bearing

1

The canvas must bleed under the panels. If the canvas is a flex sibling, a backdrop filter has nothing behind it and the glass reads as an opaque slab. Proven in pixels in the graphite doc: a magenta probe behind a panel came through as rgb(35,17,39).

2

Only the outer slab is glass. Controls, chips and selected rows are opaque. A translucent control on a translucent panel is unreadable, and the AA measurement in §6 does not survive it.

3

Icons inherit currentColor and never come from emoji. Emoji render inconsistently, cannot take a stroke weight, and break the monochrome discipline. The set here is one stroke weight throughout.

4

Icon-only controls keep a real text node. display: none removes a label from the accessibility tree entirely, which made buttons untargetable in automated checks. A visually-hidden span is not the same thing.

5

Measure at every width, and measure the axis that matters. A viewport media query is the wrong axis for a panel-width problem — this is the bug that clipped labels at some widths but not others.

6

Assert the box, then LOOK at the box. The menu's geometry was correct at every width while it painted behind the left panel and was clipped. No measurement of the menu's own rect could see that; only reviewing a screenshot could.

8 · The menu, in CSS

The whole behaviour is these rules. Note the hidden state is a translate, not an opacity alone, and the transition list differs between the two states so the exit is not delayed by the same easing.

.menus  { position: absolute; top: 44px; inset-inline: 0; bottom: 0;
         z-index: 1; }          /* over canvas (0), under toolbar (2) */

.menu  { width: 264px;
         border-top: 0;           /* the seam with the toolbar disappears */
         border-radius: 0 0 16px 16px;   /* only the bottom corners round */
         opacity: 0;
         transform: translateY(-12px);   /* tucked UP under the toolbar */
         visibility: hidden;
         transition: opacity 150ms, transform 220ms,
                     visibility 0s linear 220ms;
       }

.menu.is-open {
         opacity: 1;
         transform: translateY(0);
         visibility: visible;
         transition: opacity 150ms, transform 220ms, visibility 0s;
       }

9 · What is deliberately not here

Every one of these is a default that shows up in generated UI regardless of the subject. Each was considered and dropped.

—

No centre stack. The composition is three columns with a full-bleed canvas, because this is a tool surface, not a landing page.

—

No feature tiles. Nothing is arranged as icon + heading + sentence × 3.

—

No accent rail, no gradient wash as decoration. The only warm colour is the accent, and it marks one thing at a time.

—

No monument stat. The numbers present are real measurements of the render, in 11px tabular numerals.

—

No emoji as icons, no uppercase-as-default, no single-word italic accent.
